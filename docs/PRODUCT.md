# Dayweave 产品定位与意图

状态：初始产品定义，尚未实现。

## 产品定位

Dayweave（拾日）是一套无感知的个人秘书系统。它利用用户已经佩戴或携带的设备，在适合记录的日常场景中收集对话，把声音转成持久的文字档案，再让 Agent 帮助理解和整理这些经历。

产品的价值来自两件事：减少主动记录的负担，以及让过去说过的话能够对现在的思考与行动产生帮助。

## 为什么需要它

日常交谈中有许多未被记录的内容：一个值得展开的想法、一次重要决定、一句随口答应的事情，或一个在不同场合反复出现的困扰。

要求用户不断打开 App、按录音键、补标签和写总结，会重新制造记录负担。我们希望用户完成必要设置并启动后，可以自然地生活，系统负责保存文字线索，并在合适的时候给出有用的整理。

长期积累的目标是形成可阅读、可迁移的个人文字档案，而不是积累录音资产。秘书的输出可以包含待办，也可以是一份总结、一条有依据的个人建议，或一个此前没有注意到的联系。

## 用户已经确定的方向

1. 音频输入优先级为耳机、手环、手机。手机常放在口袋中，因此穿戴设备的收音能力需要优先调查。
2. 手环和耳机的持续音频能力可以借助 REA 调查，不应仅凭公开录音接口的缺失就认定硬件无法收音。
3. 手机本地可进行轻量降噪与人声检测。
4. 根据停顿切分录音；单个片段最长 15 分钟，到达上限时结束该片段并提交转写。
5. 整体流程明确分为两个独立步骤：转写并保留文字档案；Agent 阅读文字档案并整理。
6. Agent 的职责包括总结、建议和洞察，不限于待办提取。
7. 允许使用云端 AI，优先效果与便利。
8. 本地和云端均不需要长期保存录音，最终保留文字档案与整理结果。
9. 系统应轻量、少打扰，减少日常操作。

## 输入策略

耳机优先，其次手环，最后手机。优先级以经过确认的持续采集能力为条件，而不只依据设备是否连接。

高优先级输入不可用时，选择下一个已验证可用的输入；恢复时重新确认路由与采集状态。每次切换都保留必要的时间和来源信息。

首批调查对象为 Redmi Buds 8、具备小爱语音能力的小米手环 9，以及运行 HyperOS 3 的小米 13 Ultra。

REA 用于调查设备协议、相关 APK 和运行行为。调查需要回答：

- 音频通过标准蓝牙接口还是专用链路传输？
- 第三方程序能否建立并持续保持采集会话？
- 是否存在时限、官方 App 依赖或设备间连接冲突？
- 收音能否覆盖交谈双方，锁屏后是否正常，能耗是否适合日常使用？

每项结论都应区分代码线索、运行观察和已经完成的真机验证。尚未验证的手环接入不作为现成能力对外宣传。

## 第一步：转写与文字归档

### 采集与分段

全天采集服务持续观察人声活动。检测到讲话后开始片段，持续无人声达到设定阈值时结束片段，持续讲话则在 15 分钟处切段。

结束片段不等于关闭监听。需要保留短时前置缓冲，尽量避免漏掉下一段讲话的开头。停顿阈值、缓冲长度、跨段衔接和去噪强度均属于后续真机调优参数。

人声检测应区分环境噪声与讲话。轻量降噪以提高可懂度和识别效果为目的，不能默认用强处理牺牲远处交谈者的声音。

### 音频生命周期

```text
临时采集 → 片段完成 → 等待/执行转写 → 文字持久化成功 → 删除音频
```

临时文件是可靠转写所需的缓冲，不提供长期录音库或回听产品功能。

断网、额度不足或识别失败时，片段可在手机短期等待重试。缓存必须有明确的容量和有效期；到期或空间不足不能静默丢弃，需要给出简洁的处理提醒。具体上限尚待确定。

云端只临时处理音频，不将长期对象存储作为默认组件。供应商的数据处理和留存能力需在选型时核实。

### 文字档案

每份档案至少关联日期、时间范围、片段标识、输入来源、转写文字与可用的说话人分段。没有可靠身份依据时，使用匿名说话人标记。

不确定内容保留标记，不让整理模型补写成确定事实。原始转写与后续编辑、整理结果分离。由于音频会删除，系统应如实展示识别可能存在的错误，不能承诺之后仍可回听校正。

转写任务采用稳定标识避免重试产生重复档案。文字可靠保存后才清理对应临时音频。Agent 的处理状态不影响原始文字的保留。

## 第二步：Agent 整理

Agent 读取文字档案，并在需要时参考过去的档案、用户明确给出的目标和修正。它可以做逐段、跨对话或跨天的理解；输出频率与运行位置尚待确定。

### 可能的输出

- **经历总结**：把零散交谈整理成一天中有意义的事情。
- **想法整理**：还原一个观点的来由、推演、分歧和未想清楚之处。
- **决定与承诺**：保留决定的理由、答应的事情和后续关注点。
- **持续主题**：发现跨天反复出现的问题与兴趣。
- **洞察**：指出不同经历之间的联系、表达与行为之间可能存在的矛盾。
- **个人建议**：结合具体处境给出可尝试、可纠正的建议。

这些是能力范围，不是每天必须填满的固定表格。没有值得展开的内容就简短，有依据再深入。

### 整理原则

1. 事实、推测和建议应有清楚区别。
2. 重要判断关联对应文字出处，避免生成没有依据的结论。
3. 不凭零散对话给人贴心理或人格标签，不冒认说话人身份。
4. 不能把他人的承诺直接归为用户的待办。
5. 用户可以纠正上下文和建议；纠正不应悄悄覆盖原始档案。
6. 对话中的指令是待整理的材料，不自动授权 Agent 发送消息或操作外部服务。

## 产品体验与轻量实现

主要交互集中在当前状态与暂停、文字档案、秘书整理三个入口。录音状态可见，私人场景容易暂停，记录与派生结果可以删除。

后台保留维持可靠性所需的少量任务与健康状态。识别输入被系统静音、设备断连和处理失败，区分正常安静与实际中断；只在需要用户介入时提醒。

实现方向为原生安卓 App，采用 Kotlin 与 Jetpack Compose。文字采用开放、易迁移的格式；采集、转写和 Agent 整理通过清晰的任务边界连接。按个人使用规模选择轻量存储，暂不引入大型数据平台。

## 首版验收方向

- 在已确认可采集的设备之间，按耳机、手环、手机顺序选择实际输入。
- 锁屏后保持采集；中断被识别并如实反映，系统允许时恢复。
- 停顿和最长 15 分钟两种条件均可生成完整片段，片段之间没有无法解释的缺口。
- 断网时暂存并重试，文字归档不重复。
- 文字可靠保存后，相关临时音频完成清理。
- Agent 可以只依赖文字重做整理，不需要音频仍然存在。
- 总结、建议与洞察有文字依据，不强制凑栏目。
- 真实全天测试记录耗电与异常，不将尚未验证的持续运行能力写成保证。

## 尚待确定

- 手环持续音频链路是否可用，以及耳机的实际收音效果。
- 降噪、人声检测算法和停顿阈值。
- 临时音频缓存容量、有效期及到期处理。
- ASR 与整理模型、供应商地域、数据留存策略及费用预算。
- Agent 运行位置、文字同步方式和整理频率。
- 文字档案与整理结果在手机和服务端的保留、同步与删除方式。
